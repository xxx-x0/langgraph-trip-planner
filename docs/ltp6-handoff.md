## 本次改动

依赖沿用已通过 LTP-3/LTP-5 的环境：Python 3.12.13，后端 134 个安装分发包固定到 `requirements.lock.txt`，由 `requirements.txt` 的 constraints 引用。前端 package-lock 保留。`pip check`、安装 dry-run 及锁定版本逐项核对通过，没有升级 LangChain、LangGraph 或 MCP adapters。该基线针对本机 macOS/Python 3.12，其他平台和全新环境安装尚需独立验证；HelloAgents 旧依赖清理列入 LTP-8。

| 问题 | 当前行为 |
| --- | --- |
| 未知门票被当作免费 | 未知为 `null`，明确免费为 `0`；界面显示“票价待确认”或“免费”，预算列出未计费用 |
| 酒店按旅行天数重复计费 | N 日旅行计 N−1 晚，离开日酒店仅作位置参考；一日/两日/三日回归覆盖 0/1/2 晚 |
| 有缺项却声称在预算内 | 显示已知费用预估小计；完整且低于上限才判断在预算内，已知小计超限可明确提示，缺项且未超限时保持未知 |
| 默认只有一餐、餐次和路线时间不符 | 默认从真实候选选午/晚餐，随当前顺序和开始时间重算；使用真实路线时长，早到等待餐次/营业时段，缺餐或营业时间不明时提示。明确手动插入位置、清空餐饮和景点锁定/删除意图保留 |
| 定稿多个提交造成部分保存、重复历史或偏好计数 | 历史、草稿定稿状态及偏好在同一 SQLite 事务提交；进程内定稿串行，数据库写事务再次检查；重复返回原历史，期间草稿被编辑则拒绝保存旧快照；晚到编辑返回409 |
| 全局文案再次写错晚数、猜门票价格 | 真实复验发现“一晚234元”被写成“两晚234元”和猜测票价区间；全局费用、餐次缺项和天气说明改为直接从结构化数据生成，模型仅生成主题标语 |
| 路线出现小时单位时误作分钟 | 正确解析“1小时20分钟”为80分钟；未知路线按20分钟估算并在时间轴注明 |

持久化只增加 JSON 字段，没有修改 ORM 表结构或执行数据库升级。原业务库与起始快照的表结构、全部行逐项相同。新建验证库和旧库的列名、类型、约束及索引相同；旧景点缓存表曾追加 `open_hours`/`tel`，与新建表的列顺序不同，因此原始 CREATE TABLE 文本不完全相同。三条旧历史均可用当前模型读取，旧预算在页面提示重新核对缺项。

## 保留限制与后续

餐厅营业时间仅解析可辨认的时间窗口；日期、节假日、多组营业规则、景点闭园/预约和真实排队尚未全部建模。第一日午餐较晚，第二日有71分钟午餐前等待，能核对不表示安排已最优。旧手动餐次会按实际时刻标记，若缺少午餐则提示；不暗中移动用户手动插入位置。

每日叙述在重排后仍需点击“重写叙述”，本次两天都在最终调整后刷新；自动失效和更完整的叙述核对留给 LTP-10。最后一日酒店仅作位置参考，模型每日描述仍可能说“返回民宿”，不表示增加住宿。全局费用和天气改为结构化说明，减少自由分析；后续如增加文案，仍须保证事实不可被覆盖。旅行费用是估算，门票未知、未安排餐饮不补造价格；产品价值判断继续 UNVERIFIED。
