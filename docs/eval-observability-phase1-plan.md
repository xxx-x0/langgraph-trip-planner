## 1. 目标、范围与交付边界

首期建立一条可演示、可复查的链路：用户操作 → 执行追踪 → 业务评估 → 失败案例 → 固定数据集 → 版本对比。

首期交付物：

1. 票务推荐、AI 每日重排的完整业务 trace；发现/创建草稿链路接入基础 trace。
2. 两个评估集：18 个票务案例、12 个每日重排案例，共 30 个固定案例。
3. 独立代码评分器、少量辅助模型评分、人工参考标注、可重复运行的实验入口。
4. 项目内质量工作台：运行记录、评估实验、案例详情三个页面；完整调用树在 LangSmith 查看。
5. 带版本、来源、分母和限制的真实实验报告，以及约 5 分钟求职演示流程。

首期维持本机单用户。业务 ORM、业务 SQLite、已保存行程及当前依赖锁默认不改；实现如发现 SDK 能力不足，应先提出最小兼容方案并在隔离环境验证。新增观测产物单独存放。不得为制造改善而悄悄更换业务逻辑、降低标准或构造假成绩。

不纳入首期：公开部署/账号权限系统、付费票务接入、重新采集整套真实票价、完整前端浏览器遥测、自建通用 trace 平台、网页内批量实验调度、提示词管理平台、自动改提示词、真人满意度结论。30 个案例不覆盖项目全部能力，也不替代原 pytest/Vitest。

## 3. 评估对象与数据契约

### 3.1 两个目标、两层结果

`ticket_recommendation`：输入查询、候选批次、保存日程和缓冲；输出可行/排除集合、模型 ID、最终推荐、返回状态、预览检查结果。

`day_rearrangement`：输入单日草稿、餐饮池、路线夹具和用户 hint；输出模型原始编辑、修正后的安排、保存前后快照、返回状态。

每次执行分别评价：

- **模型层**：模型原始输出是否合法、遵守约束、满足需求。故障注入的模型输出不计真实模型质量。
- **系统层**：规则修正/回退后交给用户或保存的数据是否正确，失败是否保留状态。

例：模型漏晚餐，系统补回原晚餐。模型餐次遵循 FAIL；系统餐次保护 PASS；界面显示“已修正”，不得合并为“AI 完全正确”。

### 3.2 每个案例必须具备的字段

| 字段 | 定义 |
| --- | --- |
| `case_id / case_version / target / split` | 稳定编号、版本、目标及 dev/holdout |
| `inputs` | 查询/hint、候选、日程、明确缓冲、当前意图；不含参考答案 |
| `reference` | 可行集合、不可违反条件、预期状态与允许变更范围的独立依据；偏好答案须绑定明确的本次意图，可包含多个首选/偏序，不以单人选择代表全部用户 |
| `fixture_manifest` | 每份来源文件哈希、采集时间、数据原日期、路线/餐饮/酒店来源；原文仅本地受控留存 |
| `data_origin` | synthetic / historical_capture；后者须有可核对原始记录 |
| `execution_mode` | live_model_with_replay / injected_failure；外部工具另记 replay/live，不能合并成一个“真实”标签 |
| `expected_assertions` | 每条断言的独立 ID、规则版本、适用层和预期证据位置 |
| `annotation` | 标注人、复核时间、理由、争议及状态；无人核定保持 pending |
| `clock / random_seed` | 固定业务时钟和夹具随机种子；真实模型不承诺确定性 |

数据集采用 `trip-ticket-v1` 与 `trip-rearrange-v1`。所有案例冻结后计算内容哈希并同步 LangSmith dataset version。改输入、答案或规则均产生新版本；旧实验不被覆盖。模型可见输入与 evaluator 可见 reference 严格分开。

`run_result` 至少包含 `run_id / trace_id / experiment_id / case_id / repetition / execution_status / business_outcome / raw_model / final_output / before_hash / after_hash / checks / usage / timings / provenance`。单条 check 包含 `rule_id / layer / status / score / expected / actual / evidence_path / reason`。

`status` 取 PASS、FAIL、ERROR、NOT_APPLICABLE、NOT_EVALUATED；模型辅助评分证据不足使用 NOT_EVALUATED。无适用对象和评分器坏掉必须区分。

### 3.3 固定夹具约定

- 人工票务样本使用同一时区 Asia/Shanghai，默认旅行日期 2027-04-12～15，同行 2 人；班次 ID 为 `SYN_*`，页面标注人工示例。
- 除单独声明外，候选皆直达、有票、已知同币种同席别列表单人参考价；同行含税总价仍未知。未列出的候选差异保持相同。
- 日期与人数、城市、站点、上下文 revision 必须匹配。每条记录都写完整到发时间，不能仅存车程。
- 离开日以最后一项受保护安排结束时间 `E`、已存离开缓冲合计 `B`，人工计算最早发车 `E+B`；抵达日以到达时刻加抵达缓冲核定可用窗口。退房/行李等字段是否参与按契约分别列明，不重复累加。
- 所有路线回放必须覆盖该样本允许的活动排列和餐饮候选所需边，匹配交通方式/地点/时间口径。缺少路线夹具应 ERROR，不偷偷调用真实地图，也不捏造成功路线。
- 每日样本基础包含 A/B/C 三处不同景点、明确时长和营业区间、已存午晚餐、酒店与完整路线。使用合法字段构建，不以名称模糊匹配替代 ID/完整事实核对。
- 故障和并发在确定屏障触发，不靠不稳定 sleep；超时可使用受控时钟验证边界，报告“期限机制模拟”。

### 3.4 P5修订：产品规则、客观约束与偏好分开

2026-10-25按用户要求调整评价方法；完整定义见 [分层评估方案](eval-observability-p5-evaluation-design.md)，用户已确认 [PR01～PR03](eval-observability-p5-product-decisions.md)。本节取代“全部参考都让同一个人挑选标准答案”的解读；不改变既有数据、评分器、旧实验或pending_human门禁。

- 产品规则决定系统的调整权限、偏好缺失时的交互和模糊词的表达，不能由代理代签。
- 工程负责客观来源、区间计算、硬约束、明确指令和保存一致性，提供独立可复核证据。负责人无需替工程计算30例；要求独立人工核验的原条款仍保留，不自动放行。
- 个人偏好必须条件化：同一候选池可在不同的明确意图下有不同可接受集合；同一意图也可有多个合理答案或并列。没有明确偏好时，不计算个人最优排名，检查事实、可行性和按产品规则呈现取舍/追问。
- 价格、时长、指定席别/条件、明确日间范围、多目标取舍和未说明偏好分别设计场景。舒适不默认等于商务座；席别/价格等事实不足时不补候选、不虚构体验评分。同源偏好变体归同组，不冒充独立样本。
- 单人复核仅是单人意见；未来可由不同旅行习惯者独立判断“是否符合给定需求”，保留分歧和覆盖限制。judge只检查需求遵循和解释，不定义普遍最优。

下列30例规格仍对应已冻结的1.0.1-draft。新增偏好参数、答案集合与适用性需后续版本化落地；不得按新意图倒判既有输出、直接改gold或把新设计写成已实现。

## 5. 评分器与统计口径

### 5.1 确定性规则

| 规则 | 通过条件 / 计算方式 | 层级 |
| --- | --- | --- |
| T-VALID | ID 均在实际传给模型的集合中、无重复、数量 1～3；预期空结果时检查无需模型路径 | 模型、系统分开 |
| T-ELIG | 独立标注参考集合 G，与过滤后集合 F 精确比较；分别列误放 `F-G` 和误删 `G-F`。可行集合含未知余票并明确状态，排除候补/无票 | 系统 |
| T-FACT | 候选来源事实逐字段相等；缓冲符合“同方式沿用、变方式按已定义契约”的规则；总价和预算未知语义保持 | 系统；模型只检查实际可输出字段 |
| T-MARGIN | 余量等于参考窗口与最终时间轴差值；余量 ≤30 分钟提示紧张；0 分钟可行但紧张；负值不能通过 | 系统 |
| T-RANK | 首选在与本次明确意图相符的可接受集合中；只检查有依据的非降序/成对优先关系，允许多答案和并列；未定义偏好或参考时未评，不强求唯一首选或凑3条 | 模型、系统分开 |
| T-DISCLOSE | 未核日程、未知价/余票、列表价非同行总价、回退及紧张情况，按本例适用标记均明确；不核对无关句式 | 系统 |
| T-OUTCOME | 最终状态符合本例：推荐/无票空结果/冲突空结果/规则回退/取消/过期拒绝；正确拒绝不算业务失败 | 系统 |
| R-LOCK | 锁定活动仍存在，按当前剩余活动序列位置保持；不能仅检查锁之间的相对顺序 | 模型、系统分开 |
| R-REMOVED | 删除集合中的景点/餐次不重现、不作为插入锚点；当前保留景点集合不被静默删改 | 模型、系统分开 |
| R-MANUAL | 手动餐厅、餐次及间隙不改；依赖景点删除时遵循已确定的就近间隙规则（本期 R03 使用仍存在的 B） | 系统 |
| R-MEAL | 已安排正餐按餐次的多重集合相等，不能以非正餐替代；不补已删或从未安排的餐次 | 模型、系统分开 |
| R-FACT | 餐饮事实来自当前或候选池；坐标/价格/来源/营业时间对应同一对象；非模型可写字段不受模型伪造值影响 | 系统 |
| R-DURATION | 每个已保留景点游览分钟不缩减，不能通过缩时制造“更轻松” | 系统 |
| R-REST | 固定休息开始/结束/区域保持，时间轴无重叠；不伪造回酒店路线 | 系统 |
| R-WINDOW | 时间轴、已知营业窗口、餐次、抵离窗口均满足独立参考；路线失败不保存估算成功结果 | 系统 |
| R-INTENT | 明确请求逐项完成；保存了安全旧方案但没执行调整，记 0；无法满足且明确拒绝只在本例允许拒绝时通过 | 模型、系统分开 |
| R-ROUTE | 用同一组路线事实计算交通分钟；`delta=baseline_minutes-final_minutes`；本例要求改善时 delta>0 且全部硬约束通过 | 系统质量 |
| R-DISCLOSE | 发生修正/保留原安排时，事实说明与实际结果一致；不能显示“已按要求调整”而实为未变 | 系统 |
| S-PERSIST | 只读推荐前后业务状态相同；成功重排仅允许目标日及规定派生字段变化；失败无写入；CAS 拒绝不得覆盖并发最新值 | 系统 |
| S-TRACE | 操作关联唯一、子步骤完整结束；记录取消/超时/修正/回退；不串行程、不重复计算一次实际模型用量 | 观测 |

上述规则的P5偏好语义为方案修订，现有rules-v1.1实现和旧报告未改变；新适用性/参考须另建版本验证后才使用。

系统硬约束集合为 T-VALID、T-ELIG、T-FACT、T-MARGIN、T-DISCLOSE、T-OUTCOME、R-LOCK、R-REMOVED、R-MANUAL、R-MEAL、R-FACT、R-DURATION、R-REST、R-WINDOW、R-DISCLOSE、S-PERSIST 的**系统层适用项**；T-RANK、R-INTENT、R-ROUTE 和 J-* 为任务质量，不混入安全合格率；S-TRACE 为观测质量。模型层违反但系统修复的结果不能拉低“系统保护正确率”，也不能抹掉模型错误。

拒绝/取消等预期无输出案例，时间轴等输出专属规则为 N/A，状态与不写入检查仍须 PASS；否则无法通过。R08 这类原输入本身有冲突的案例，只检查是否避免写入新的违规结果，不把保留原始输入误报成一次新保存违规。适用矩阵在执行前冻结，不能看见失败后改为 N/A。

独立核定要求：评分器不调用生产 `ScheduleCheck.evaluate`、`multicity.projection`、`schedule_day` 来生成预期答案。小样本用人工计算表/独立区间检查验证。可以读取生产输出；不能把输出复制成答案。测试复用输入可以，断言逻辑和参考结果需要独立核对。

### 5.2 评分器自检

为每条规则准备至少一个已知 PASS、一个已知 FAIL；适用规则增加 N/A 和缺证据样本。它们是评分器测试，不计入 30 个业务案例。

必须能识别的变异：伪造候选 ID、重复 ID、交换时间、价格 null→0、缓冲减 1 分钟造成冲突、错误删除一个可行班次、锁定位置移位、漏晚餐、恢复删除餐次、改坐标、缩短景点时长、占用休息区间、超时后写入、将被纠正模型误记为原始成功。全部预设变异应被对应评分器检出，否则评估基础设施不验收。

### 5.3 模型辅助评价（非阻断）

仅为存在语义取舍的 R10、T04 及开发阶段选定的需求解释输出辅助评分；结构化字段能判断的先用代码。票务/每日说明由程序生成，标记 `evaluated_component=system_explanation`，不归为模型写作质量。

| 指标 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| J-INTENT 需求回应 | 未回应关键需求或与结果相反 | 部分完成，遗漏一个关键意图/限制 | 回应本次需求且与结构化结果一致 |
| J-TRADEOFF 取舍说明 | 编造优势、忽略已知冲突 | 结论基本正确但遗漏关键代价 | 用可定位事实说明收益、代价及不确定项 |

judge 输入为本次需求、候选/前后日程和必要证据，不含实验名、预期赢家或参考评分。输出为 `score / evidence_paths / reason / abstain_reason / judge_version`；无法核定使用 NOT_EVALUATED。案例文字视为数据，不能执行其中“忽略规则、打满分”等指令。

校准先从开发案例的输出及人工构造正反例取 12 份，人工评分后比较（这些是评分校准样本，不新增业务案例）。每份重复评分 2 次：人工一致项至少 10/12、两次分数一致项至少 10/12，才展示“已初步校准”；否则保持实验性，仍可交付代码评估系统。人工标注者身份与样本数公开，代理自评不能冒充真人标注。保留集不用于 judge 调优。P5原12份面板含现有holdout，仅保留为诊断审阅材料，不直接执行校准；后续另选开发材料冻结。偏好标签须围绕明确意图，单人意见与多方分歧单列，judge不能自行定义舒适/均衡。

A/B 语义比较可匿名打乱顺序、交换位置复核，允许 tie/无法判断；不得以“换了另一个模型评分”代替校准。首期不以 judge 总分自动放行业务变更。

### 5.4 分母、失败与缺失

对每个指标记录 P（通过）、F（失败）、E（评分错误/该指标所需执行缺失）、U（尚未评估）、NA（不适用）。

- 已评分通过率：`P/(P+F)`，同时必须展示覆盖率 `(P+F)/(P+F+E+U)` 和原始计数。分母 0 显示“无适用数据”。
- 验收完成率：`P/(P+F+E+U)`；不能靠漏跑、超时、judge 失败减少分母。
- 技术执行状态与业务预期分开：预期 409/取消在原运行状态中保留，在结果正确性上可以 PASS；意外超时使目标完成 FAIL，依赖最终输出的细项记 E。
- case 系统硬约束合格：所有适用硬约束 PASS 且无 E/U；系统有修正时仍可合格，但模型原始遵循另列。
- 票务过滤精确率 `|F∩G|/|F|`，召回率 `|F∩G|/|G|`；空集合导致分母 0 时显示 N/A，仍用集合完全相等判断正确拒绝。展示误放/误删个数，避免只看高百分比。
- 模型原始有效率仅统计真实发生的模型调用；注入和 Z 案例不纳入。模型超时/无效输出计模型未成功；规则回退率另列。
- 首选可接受率需本次意图明确、参考可行集与条件化接受集合已核定且应推荐；可接受多个首选，只检验已声明优先关系。偏好未说明/参考待审保留U，需取证却缺证据记E，预期无需排序才N/A；展示应评数、可评数和缺评原因，失败不能从计划分母删掉，不用“所有候选都是gold”代替未评。
- 既有30例仍按原案例等权展示；新增偏好设计须按偏好类别分层，候选级micro另列，同源变体和重复不冒充独立案例。整体权重、来源家族分组与覆盖率在新实验前冻结，避免T18的80候选或多造简单偏好场景淹没其他案例；dev/holdout、正常/注入、模型/系统分列。
- p50/p95 用已完成运行的单次操作墙钟按固定 nearest-rank 方法计算；超时/取消数量和耗时另列。少于 20 条时 p95 标“小样本，仅描述”。并行子 span 时长不可直接相加当墙钟。
- token 只取服务返回 usage；缺失为 null。费用按模型/日期对应费率估算，记录币种、费率来源、缓存计费项；缺费率/用量不填 0。judge、被测模型、观测平台费用分列。

## 6. 实验协议与改善判断

### 6.1 比较方案

| 目标 | 基线 | 当前方案 | 候选方案 |
| --- | --- | --- | --- |
| 票务 | 与当前完全相同的可行性过滤＋纯规则排序，不通过伪造网络故障实现 | 冻结当前模型、提示词和配置 | 后续明确提出的一个提示词/策略变化；保护规则保持相同 |
| 每日重排 | 保留原安排 no-op，作为安全和需求完成的参照，不宣称等价智能重排 | 冻结当前 AI 重排链路 | 后续提出的一个可解释变化 |

候选方案未授权/未实现时，可以先比较规则/no-op 与当前，不虚构“优化版”。no-op 在 R01/R02 等需改变案例上自然不满足需求。不同方案某层无模型时该层 N/A，不能计 100%。故障注入在无模型基线上不适用，必须按方案声明适用矩阵。

### 6.2 运行顺序与成本边界

1. 兼容性 spike：隔离环境验证现锁 `langsmith==0.8.9` 的追踪、异步评估、反馈写入、脱敏和报告读取。当前官方示例可能晚于锁版本，不能直接照搬后自动升级。
2. 本地固定输出自检：30 个夹具 schema、评分器正反例及隔离库检查通过；不发真实模型请求。
3. dev 20 例运行基线和当前方案各一轮；缺失/失败完整记录，先修评估器问题，修改后升版本重跑。
4. 冻结数据、评分器和方案后，30 例完成基线/当前正式比较；已有相同 manifest 的 dev 结果可复用并标明。
5. 对正式比较中 20 个真实模型案例，当前方案各重复 3 次，故障 8 例和 Z 2 例各一次；每个 AI 方案应有 70 条计划记录（20×3＋8＋2），其中模型尝试/重试数另计。前一步的一次正式结果计入这 3 次，不额外变成第 4 次。运行失败仍占原计划槽位，重试实验生成新记录。
6. 若后来加入候选方案，使用同一冻结协议，独立报告；两种 AI 方案最多 140 条计划记录，不含基线、自检和 judge。调用前显示估计 token/费用及上限，只有明确开始实验才调用；本方案不授权此刻执行。

运行器必须有模型请求数、总 token/费用预算（未知费率时用请求数/token 限制）、总墙钟上限、并发上限、取消与断点续跑；不无限重试或自动循环优化。默认并发 1，不超过现有外部服务边界。评分调用与业务调用成本分别记录。执行参数写入 manifest，开始后不得静默放宽。

固定外部回放不调用新地图/票务；新实查另建实验。固定业务日期/时钟，记录模型服务实际执行时间；旧报价不能用于判断今天价格。三个重复是稳定性检查，不是把 30 个独立样本变成 90 个，也不主张统计显著性。

### 6.3 版本清单

每个实验必须记录：源码 commit＋dirty patch/必要未跟踪源码内容哈希、依赖锁哈希、dataset version/hash、route fixture hash、模型 ID 与可得服务版本、温度/结构化/思考模式、prompt hash、evaluator version、judge 配置、运行参数和脱敏版本。排除 `.env`、业务 DB、个人资料、日志等敏感文件，不为计算版本哈希打包整个目录。

### 6.4 两类结论分开验收

**评估能力交付**：能够正确运行、记录、评分、比较和定位失败；现有模型可能得低分，不影响“已经建立可信测量能力”。

**业务方案可采用**：建议以系统硬约束 100% 适用检查通过、无新增误放/事实错误/非法写入为门槛；首选可接受率或需求完成率至少一个预先选定主指标改善，其他关键指标无退步。若有退步，逐例列出，由用户判断取舍，不能自动称更优。主指标应在候选实现前冻结：票务用符合明确本次意图的T-RANK首选可接受率，并分偏好报告；未说明偏好另看事实/交互，不以未知排名填满分。重排用明确目标下R-INTENT完成率；减交通时间不代表通用舒适。新增偏好方案的总体权重与配对规则须先冻结，同一意图的A重叠时不强求输出变化。

首次报告建立基线，不强求人为规定“提升 20%”。耗时与费用作为并列结果；若质量无收益且成本增加，应报告不支持采用该 AI 方案。复杂质量评分不抵消硬约束错误。

## 7. Trace 与 LangSmith 组织

### 7.1 根操作与关联

一次用户/API 操作为根 trace，不将跨小时的人为编辑过程硬塞进一个运行。session 用不透明本地映射关联同趟旅行；记录匿名 draft/trip 关联、revision/basis 摘要、operation_id。相关 trace 以 session/metadata 查询，不把业务 user_id 当认证。

票务子步骤：读取快照 → 候选资格/日程核对 → 模型选择 → 原始输出校验/规则回退 → 快照再次核对 → 返回。采用预览是独立关联 trace。

重排子步骤：读取快照 → 模型建议 → 锁定/餐饮修正 → 路线计算 → 时段核对/有限恢复 → 事实说明/预算 → CAS 保存。

外部调用 span 下区分排队、尝试、重连/退避、缓存命中；使用单调时钟计耗时。LangChain 自动模型 span 与公共封装避免重复嵌套计算用量。异步任务、图并行节点、SSE 响应体、取消/异常都要正确关闭和传播上下文。

首期为 ticket/day_rearrange 做完整业务语义追踪；发现和创建草稿只做 API/图/外部调用基础追踪，其他编辑不声称全覆盖。结构化事实仅在本次操作中存在才记录，不恢复隐式历史偏好加载。

### 7.2 环境、上传与隐私

建议项目名 `trip-planner-dev`（实际开发操作）、`trip-planner-eval`（评估）、`trip-planner-demo`（明确的隔离演示）；最终实验绑定 dataset 和 experiment ID。不得把演示流量混入实际用户使用量。

上传采用字段白名单：保留公开 POI/候选、必要日程时刻和匿名约束；移除身份证、电话、邮箱、个人地址、账号、Cookie、认证头、密钥和无关原文。自由文本 hint 也做脱敏；业务 ID 用稳定不透明映射。脱敏可能改变语义时标注输入差异，人工复核该案例是否仍可评。

必须在 SDK 导出前处理，覆盖根 trace、自动子 run、metadata、异常、模型 prompt/response、dataset、feedback。仅过滤普通 logger 不足。票务页面原文继续不进入 API。评估使用的原始本地证据与上传副本分开；本地报告也只缓存可展示的脱敏版本。

官方支持上传前隐藏/处理输入输出，但具体 API 要与锁版本验证：[敏感数据处理](https://docs.langchain.com/langsmith/mask-inputs-outputs)。

导出异步有界；建议应用可控队列上限 1000 事件、关闭等待最多 2 秒，满队列/不可达记 dropped/export_failed，不阻塞规划、不修改原业务超时。如锁定 SDK 无法满足边界，用最小应用适配层实现或记录 spike 阻塞，不能假设后台线程天然无限安全。

### 7.3 本地报告与在线检查

独立配置 `OBSERVABILITY_DIR`（拟定），存脱敏运行索引、不可变实验 JSON、评分明细和导出状态；不写业务 DB。写入原子化、按 ID 去重，刷新不重复计数。建议运行记录保留 30 天/上限 200 MB，达到任一阈值清理最旧记录；明确固定的演示实验报告不自动清理，展示磁盘占用。LangSmith 云端保留期按账号实际配置确认，不把本地策略当云端保证。

实际操作后可异步做能从本次数据判断的约束检查；没有人工参考集时不能在线计算真实过滤召回率/偏好最优率。首期在线规则全量、在线 judge 默认关闭，用户主动启用再按采样和预算运行；离线 judge 与在线配额分开。

失败记录先进入待复核清单，开发者审核脱敏、补答案后用开发命令入库，创建新 dataset version；首期网页只读，不实现一键自动把失败当正确答案。参考：[评估运行](https://docs.langchain.com/langsmith/evaluate-llm-application)。

## 8. 质量工作台页面结构

本节为原定契约；P4 本地报告实现及云端范围差异见 [P4 交接](eval-observability-p4-handoff.md)。入口在开发/演示模式出现，正常行程页只提供轻量“查看本次执行”关联；关闭观测时隐藏入口。权限仍限本机，不能靠隐藏菜单支持公开部署。LangSmith 服务端密钥不进入前端 bundle/localStorage，首期不启用公开 trace 分享。

### 8.1 页面 A：运行记录 `/quality/runs`

自上而下布局：

1. 标题“质量工作台”，二级导航“运行记录 / 评估实验”；右上显示环境、数据更新时间、连接/导出状态。
2. 筛选：时间范围、票务/重排/发现/创建草稿、实际使用/回放/故障、技术状态、业务结果、模型/规则、是否存在规则失败。
3. 摘要：操作数、业务预期符合数/适用数、技术错误数、规则回退数、p50/p95、token 与费用覆盖率。所有数字跟随同一筛选，不能把失败过滤掉后仍声称总体成功率。
4. 运行表：时间、操作、匿名旅行/版本、来源模式、技术状态、业务结果、硬约束检查、回退/修正、耗时、用量、trace 上传状态。
5. 每行进入案例详情；有重复请求/关联预览时提供关联记录，保留各自独立 ID。

空状态：“尚无运行记录”；未配置：“尚未连接 LangSmith，本地记录状态…”；离线：“正在显示截至…的缓存”；丢失 trace：“本地报告可用，云端追踪未成功上传”。不生成演示数字填空。

### 8.2 页面 B：评估实验 `/quality/experiments`

1. 选择目标、数据集版本、dev/holdout/全部、来源/执行模式；不同来源默认分组。
2. 实验卡/表：实验名、方案、源码/prompt/evaluator 版本、完成计划数、真实模型数、注入数、日期、运行/部分完成/失败/取消状态。
3. 勾选 A/B 进入并排比较：同 dataset、评分器和夹具版本时才计算正式差值；不一致显示“不具可比性”，可查看但不默认排名。
4. 指标表分为系统硬约束、模型原始遵循、任务质量、运行成本四组。每格显示 P/F/E/U/NA 和分母，可展开重复执行范围。无综合百分制大表盘。
5. 变化清单：改善、退步、不变、无法判断；可按规则过滤；每项点入同案例 A/B 详情。输入相同才自动配对，按 case/repetition 对应。
6. 导出当前真实脱敏报告；“在 LangSmith 比较”链接；页面不直接触发批量模型实验。

正式改善/退步对确定性指标按同例差异判定；多次模型结果显示 0/3、2/3 等，不把一次好结果替换其余结果。judge 分歧单列。支持平台原生详细比较：[实验对比](https://docs.langchain.com/langsmith/compare-experiment-results)。

### 8.3 页面 C：案例详情 `/quality/runs/:runId`

标题区展示 case/run ID、操作、日期、版本、来源、技术状态、业务结果、评分状态，以及“完整追踪”链接。实验比较从 query 参数关联另一 run；刷新后仍定位相同对象。

桌面主区三列，手机依次堆叠：

| 区域 | 票务案例 | 重排案例 |
| --- | --- | --- |
| 输入事实 | 当前日程、日期/同行人数、缓冲、候选来源和查询偏好 | 原时间轴、锁定/删除、手动餐饮、休息、用户 hint |
| 执行/结果 | 全部候选可搜索；保留/排除理由；模型原始 ID 与最终推荐并列 | 模型原始建议、系统修正、最终保存时间轴，标出变化/保留/拒绝 |
| 评估证据 | 预期可行集合和首选集合；逐条 actual/expected/理由 | 逐项约束、需求是否完成、原/新交通分钟、保存前后快照差异 |

下方简化步骤时间线可展开耗时/尝试/回退；点击评分项定位对应活动或班次。不给每个候选都建立一个庞大子 trace，完整候选核对结果可作为结构化步骤产物。

操作按钮限定为：返回来源、复制匿名 run ID、导出脱敏记录、在 LangSmith 查看；首期不在此编辑行程、改分、启动重跑或自动创建数据集。

所有外部文本按纯文本渲染，状态不能只靠红绿颜色；键盘可操作，390px 宽度无整体横向溢出，深浅色与减少动态效果可用。复用现有 Ant Design Vue/样式，不引入图表依赖；首期表格、时间条和差异标记足够。

### 8.4 拟定只读接口

| 接口 | 输出契约 |
| --- | --- |
| `GET /api/quality/status` | 启用状态、云端可达/导出状态、缓存时间、丢弃数、SDK 版本和配置完整性；不返回密钥 |
| `GET /api/quality/runs` | cursor 分页、明确筛选、总数/是否完整、同筛选摘要、来源和上传状态 |
| `GET /api/quality/runs/{id}` | 脱敏详情、逐条评分、关联操作、验证过的 LangSmith URL |
| `GET /api/quality/experiments` | 数据集/版本、计划数、完成数、方案、状态、指标及覆盖率 |
| `GET /api/quality/experiments/compare?left=...&right=...` | 可比性结果、配对规则、逐例差异、未配对/缺失项；不能只做数组下标对齐 |

前端只读后端标准化结果。后端读本地报告并按需刷新云端；外部不可用时返回缓存时间和局限，不能假装实时。完整 LangSmith 链接使用 SDK/验证过的实际结果生成，不猜测 workspace URL，不通过 iframe 嵌入登录态。

| A09 可复现 | 基线与当前在同冻结集运行；AI 20 例×3＋故障/无模型 10 例×1 共 70 计划记录完整，失败也保留；manifest 齐全 | 两目标实验报告、70 槽位对账、源码/配置/数据/评分版本；不要求模型输出完全相同 |
| A10 隔离 | 每次实验明确隔离数据库，正常/故障/取消均不污染业务库或其他重复；回放未请求新供应商 | 测试数据库路径、网络目的地审计、业务库文件校验/只读确认；不读取密钥内容展示 |
| A11 页面可信 | 三页能筛选、A/B 配对、定位失败证据并打开实际 LangSmith 链接；无记录、部分完成、无配置、离线/上传失败均有明确状态 | 浏览器走查及与真实报告对账；无写死 KPI/示范分数；刷新后 run/实验选择保持 |
| A12 UI 可用 | 1440px 桌面、390px 手机、深浅色、键盘、减少动画；来源/状态有文字，外部文本无 HTML 执行 | 实际页面截图/交互检查；筛选和返回保留上下文 |
| A13 回归 | 后端相关与全量普通测试、前端测试和构建通过；外部 smoke 跳过明确列出；依赖无未经验证升级 | 明确临时 DATABASE_URL 的测试报告、构建结果与锁 diff；不沿用旧通过数字 |
| A14 展示闭环 | 演示中从一个失败运行到案例、实验差异及 trace；至少展示一个局限或未改善项 | 约 5 分钟演示步骤、真实报告和链接；全绿时可用明确标注的注入失败，不伪造真实事故 |
| A15 辅助评分 | judge 12 份人工校准与重复性达到 10/12 才标“初步校准”；否则维持未校准/实验性 | 人工评分、judge 两次输出、分歧记录；无真人参与不得标人工完成；不阻塞代码 eval 交付 |
| A16 业务效果 | 系统硬约束无失败/缺评、无新增事实/写入错误，主质量指标按预先冻结口径比较 | 每例原始结果与改善/退步表；未达标时只能交付测量能力，不能宣称方案质量已验收 |

A01～A14 为首期评估系统交付门槛；A15 是辅助 judge 成熟度门槛；A16 是业务方案效果结论，独立验收。业务模型不合格不能被伪装成评估系统缺陷，也不能因为评估平台能运行就宣称业务合格。所有阈值是本方案拟定，需在实施前随方案冻结；不依据结果倒推门槛。

## 11. 求职演示与最终报告模板

建议演示顺序：

1. 约 40 秒：展示旅行应用和本次推荐需求，说明存在固定日程与接驳约束。
2. 约 60 秒：打开一条实际失败/明确注入记录，展示候选被误选、模型失败或规则纠正的位置。
3. 约 60 秒：打开 LangSmith，沿根操作看模型、工具、校验及耗时；说明图外业务也被追踪。
4. 约 80 秒：同案例 A/B 比较，解释数据集、参考答案、硬约束及模型/系统分层；展示一项退步或未解决问题。
5. 约 60 秒：展示全体实验统计、样本数/缺失/成本、版本信息，解释是否值得使用 AI 及下一步要补什么证据。

正式报告包含：版本与日期、案例分布、基线定义、全部计划执行与完成数、系统硬约束、模型原始遵循、首选/需求质量、耗时与费用覆盖率、改善与退步明细、评分器自检、judge 校准状态、隐私/无扰动验证、真实与模拟范围、USER 判断。

简历可陈述“建立覆盖 30 个旅行规划场景的评估集，接入 LangSmith trace 与版本对比，并实现约束/事实/模型输出分层评价”。只有完成并有报告后才能使用此表述；百分比改善、生产稳定性和用户满意度必须另有对应证据。
