# 地理编排、草稿用餐区与酒店展示清理

**日期**: 2026-05-22
**作者**: Codex + finn
**状态**: 待实施

## 背景

本次反馈集中在三个已有流程的可理解性：

1. Discover 页的“智能编排”虽然已经先按地理位置聚类，再按游玩时长重平衡，但界面会出现第 1 天接近 8 小时、后续天数较空的结果，容易让用户理解成“先塞满第 1 天再排其他天”。用户明确希望相近景点优先安排在同一天。
2. Draft 页把“加用餐”入口放在每个景点行后面，并把餐食的内部分类值 `main` 直接显示给用户。这个布局把景点顺序编辑和用餐编辑绑得过紧，也暴露了实现字段。
3. Result 页酒店卡片对外部酒店数据过于直接：失败图片仍占据大面积区域，酒店描述中的 HTML 标签被当作普通文本显示，缺少价格时也没有明确降级。

## 目标

- 智能日程预览继续以地理邻近关系为主，时长信息用于提示和有限平衡，不把相近景点为了填满时长轻易拆散。
- Draft 页将景点顺序和用餐编辑拆成同一天内的两个独立区域。
- Draft 页不再显示内部分类值 `main`，展示用户能理解的中文标签。
- 酒店卡片不再展示失败图片占位，描述以干净文本显示，价格缺失时给出明确可理解的降级文案。

## 非目标

- 不改变用户拖拽景点顺序的能力。
- 不把用餐安排做成精确到早中晚时间轴的编辑器。
- 不为酒店图片另接新的图片服务，也不在前端猜测酒店价格。
- 不重写 AIGoHotel 搜索协议，只清理当前已拿到字段的映射和展示。

## 设计

### 1. Discover 智能编排

预览接口仍保留“估算游玩时长 + 地理聚类”的流程，但编排优先级明确为：

1. 先按坐标把相近景点分成每日簇。
2. 时长仅在某一天明显超出 8 小时且能保持目标日地理合理时做有限调整。
3. 调整后仍保留每天的预计时长和“当天偏紧”提示，让用户看到负载差异并手动拖拽微调。

测试要覆盖一个近邻簇和远端簇的场景，确保重平衡不会只因为某天时长更满就把近邻景点拆到远端日程。

### 2. Draft 用餐编辑

每个 DayCard 的内容区拆为：

- `景点安排`：仅保留可拖拽的景点行。
- `用餐安排`：独立显示当日餐食列表和一个统一的“添加用餐”入口。
- `路线`：沿用当前路线段展示。

统一添加入口仍复用现有候选池和自定义餐食能力。新增用餐不再从某个景点行取锚点，而由当前后端重算逻辑使用默认落点；已有餐食携带的 `insert_after` 字段继续透传，避免破坏已装配草稿。

餐食行上的分类展示走中文映射：

- `main` -> `正餐`
- `snack` -> `小吃`
- `dessert` -> `甜品`
- `cafe` -> `咖啡`
- `late_night` -> `夜宵`

已有早餐、午餐、晚餐类型也应展示为中文，而不是原始字段值。

### 3. 酒店信息展示

酒店数据进入展示前做两层处理：

- 后端酒店解析清理富文本描述，把简单 HTML 标签移除并规整空白。
- 酒店价格字段继续只展示真实解析出的数值；解析不到时前端显示“价格待确认”。

酒店卡片图片改为可选展示：

- 有可用图片且加载成功时展示。
- 没有图片时不生成装饰性占位图。
- 图片加载失败时收起图片区域，不再显示“图片加载失败”的大块占位。

这样结果页先保证酒店名称、星级、地址、距离、设施和描述可读，不让外部图片失败主导卡片。

## 错误处理

- 无坐标景点仍走现有兜底分配逻辑。
- 餐食候选池为空时保留现有自定义添加能力。
- 酒店描述为空时不显示描述区；价格为空时仅显示降级文案，不伪造金额。

## 验证

- 后端测试覆盖地理编排的邻近性约束和酒店描述/价格字段解析清理。
- 前端构建覆盖 Draft/Result 组件改动的类型检查。
- 在本地浏览器检查 Discover 分配预览、Draft 单日用餐区、Result 酒店卡片在桌面和移动视口下的实际展示。
