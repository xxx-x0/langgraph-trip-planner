## 评分可靠性与使用边界

评分器独立检查班次事实、集合、偏好、缓冲、锁位、删除、餐次、固定休息、营业/交通区间、保存状态、Trace 等，不调用生产 ScheduleCheck、multicity.projection 或 schedule_day 生成答案。R10 原始建议与最终系统安排分开评价；系统恢复旧安排不抹去模型违约，也不冒充用户意图已满足。S-PERSIST 在并发场景对比最新状态，T17 保留两个 409 检查点，取消后额外调用、有限恢复和 110 秒期限各保留证据槽。

依赖待确认参考的规则默认 NOT_EVALUATED；显式 `--allow-provisional` 才计算诊断值，仍标 provisional。缺证据、缺方向路线、评分器异常为 ERROR，未适用为 NA，不悄悄删除失败或当零分成功。T18 排名未定义，即使诊断也不会填答案。对系统解释的文本规则校验当前中文模板标记，通用语义仍须人工/经校准 judge，不夸大代码规则能力。

模型质量只统计与计划模式一致的真实模型执行，故障注入、自检、no-model 各自分组。汇总保留 P/F/E/U/NA，已评分通过率、覆盖率、完成率分开，空分母为 null，重复 case/run 拒绝重复计数。`selftest` 标记 SCORER_SELFTEST_ONLY，使用已知输出替身，实际模型调用和正式案例验收均为 0。

后续 P3 必须实现独立运行器和证据投影：从业务执行收集未修正模型结果、最终响应、实际过滤集合和保存前/最新/后完整事实，而不是从参考生成 Observation。运行期 ID/默认值的标准化及实际 JSON 保存边界需在运行器中验证。目前只验证契约、原生模型 schema 兼容和评分器，未声称 30 个业务流程全部实际回放成功。
